# Baseline Build Plan

## Scope

Build the intentionally small baseline checkout application defined in `REQUIREMENTS.md`. This plan does not add features beyond those requirements.

## Technology choices

- **Application:** Next.js with the App Router and a `src/` directory.
- **Language:** strict TypeScript.
- **Test runner:** Vitest. It is lightweight, works well with TypeScript, and supports a simple one-shot `test:ci` script without requiring browser automation for the required placeholder test.
- **Styling:** one global CSS file only; no Tailwind, component library, or CSS-in-JS package.

## Project setup

Create the application with the official Next.js scaffold rather than hand-writing the base project files. From the parent directory, use a command equivalent to:

```sh
npx create-next-app@latest my-app --yes --app --src-dir --typescript --use-npm --no-tailwind
cd my-app
npm run dev
```

The explicit flags retain the requested default Next.js creation workflow while ensuring the scaffold meets the course requirements: App Router, strict TypeScript, a `src/` directory, npm scripts, and no Tailwind. The project root for the baseline application will be `my-app/`; course artifacts should be kept with that project root.

## Product catalogue

`GET /api/products` will return exactly this in-memory catalogue:

```json
[
  { "id": "prod-001", "name": "Enamel Mug", "price": 12.5 },
  { "id": "prod-002", "name": "Canvas Tote", "price": 18.0 },
  { "id": "prod-003", "name": "Wool Beanie", "price": 22.75 }
]
```

Prices remain JavaScript floating-point dollars throughout the baseline.

## API implementation and request flow

1. A visitor opens the home page and follows its link to `/checkout`.
2. The checkout page obtains or uses the hard-coded product choices and constructs a request body containing a client-supplied `userId` and cart items.
3. The checkout page sends the body to `POST /api/checkout`.
4. The checkout route parses the body as JSON. Malformed JSON immediately returns HTTP 400 and `{ "error": "<human-readable message>" }`.
5. The route validates that `userId` is a non-empty string and `items` is a non-empty array.
6. For every cart item, the route confirms a known `productId` and a present, positive integer `quantity`. Any invalid cart returns HTTP 400 with the defined error shape.
7. The route resolves every price from `src/lib/products.ts`, never from the request body, then calculates the subtotal as the sum of `unitPrice × quantity`.
8. The route calls `calculateDiscount(subtotal)` from `src/lib/pricing.ts` and calculates `total = subtotal - discount`.
9. Because the approved pricing stub returns `0`, the success response is HTTP 200 with `{ "total": number }`.

## Tests and acceptance checks

- `npm install` completes successfully.
- `npm run dev` starts the Next.js development server.
- `npm run build` completes successfully under strict TypeScript.
- `npm run test:ci` executes the placeholder Vitest test successfully.
- `GET /api/products` responds with HTTP 200 and exactly the specified three products.
- A valid `POST /api/checkout` responds with HTTP 200 and `{ "total": number }`.
- Checkout uses catalogue prices only, even if a client sends an extra price field.
- A malformed JSON body returns HTTP 400 with `{ "error": "<human-readable message>" }`.
- Each of the following returns HTTP 400 with the same error shape: missing, empty, or non-string `userId`; missing or empty `items`; an unknown product ID; and zero, negative, non-integer, or missing quantity.
- `src/lib/pricing.ts` exactly contains the approved no-op stub and no other contents.

## Constraints and how they will be satisfied

| Constraint | Plan response |
| --- | --- |
| App Router, strict TypeScript, and `src/` | Use Next.js App Router routes under `src/app` and strict TypeScript configuration. |
| Required endpoints | Create only the specified product read route and checkout write route. |
| In-memory only | Store the catalogue in a TypeScript module; add no database or data file. |
| No authentication | Treat `userId` as a client-supplied non-empty string and add no auth logic. |
| Sensitive pricing module | Create the exact approved stub once; make no later content change without explicit human approval. |
| Floating-point dollars | Use JavaScript numbers and make no rounding, decimal, or minor-unit changes. |
| Minimal styling | Use one global CSS file with a system font, one accent colour, rounded UI, a centered max-width container, and consistent spacing. |
| No extra infrastructure | Add no external services, Docker, database, Tailwind, component library, or CSS-in-JS package. |
| Small scope | Limit application work to the named pages, routes, catalogue, pricing stub, README, and placeholder test. |

## Assumptions and risks

- The exact checkout controls are not specified. The UI will stay minimal while ensuring it posts the required request shape.
- The requirements deliberately permit floating-point results; no special monetary rounding will be introduced.
- Validation error messages may vary in wording, provided they are human-readable and use the required HTTP 400 error shape.
- `pricing.ts` is sensitive. Any later request that would alter its exact stub must be paused for explicit human approval before editing.
